# QA-отчёт — 2026-08-18

Ручное тестирование через браузер (claude-in-chrome, localhost:3000 + продовий бэкенд shopmarker-backend.onrender.com). Скоуп: головна → каталог → товар → кошик → checkout → реєстрація/логін, плюс перевірка на брейкпоінтах mobile (~500px) / 768 / 1280 / desktop.

Статус: **повний флоу оформлення замовлення пройти не вдалося** — три окремі блокери (п.1–3). Решта — знайдені під час тестування дефекти різної ваги.

## 1. [BLOCKER] Реєстрація не працює в dev — hCaptcha не рендериться

**Де:** `components/common/AppCaptcha.vue`, `nuxt.config.ts:111-114`

Форма реєстрації (модалка «Увійти/Реєстрація» з іконки профілю) використовує офіційний тестовий sitekey hCaptcha (`10000000-ffff-ffff-ffff-000000000001`), захардкоджений для non-production:

```ts
hcaptchaSiteKey:
  process.env.NODE_ENV === 'production'
    ? process.env.NUXT_PUBLIC_HCAPTCHA_SITE_KEY
    : '10000000-ffff-ffff-ffff-000000000001',
```

Замість інтерактивного чекбокса «Я не робот» віджет показує власну помилку:

> «Эта hCaptcha используется в целях тестирования. Пожалуйста, свяжитесь с администратором сайта, если вы видите это.»

Мережа до `hcaptcha.com` доступна (локаль `ru.json` віддається 200 OK) — проблема не в блокуванні мережі. Форма валідує «Пройдіть перевірку капчі» і не дає відправити реєстрацію. **Ніхто не може зареєструватись локально**, поки це не полагоджено.

**Наслідок для тесту:** довелось спробувати увійти замість реєстрації — див. п.2.

## 2. [Info] Автозаповнення браузера не спрацьовує для автоматизованого вводу

Форма логіну підхопила збережені Chrome credentials (`Harington@gmail.com`), але синтетичний ввід (без справжнього user-жесту) не тригерить нативний dropdown автозаповнення — поле не вдалося перезаповнити самостійно, пароль у відкритому вигляді невідомий. Не баг застосунку, обмеження інструменту тестування — але саме через це не вдалося увійти під існуючим акаунтом і довелось тестувати checkout як гість.

## 3. [BLOCKER] Гостьовий checkout: форма гостьова, бекенд — ні (401)

**Де:** `stores/cart.ts` (фронт, форма коректно дає оформити без логіну) vs `shopmarker-backend/src/modules/orders/orders.routes.ts:184`

Сторінка `/checkout` повністю доступна без авторизації: не редіректить на логін, дає заповнити одержувача, обрати «Відділення Нової Пошти» (автокомпліт міста/відділення працює, тестово обрано м. Київ, Відділення №1), спосіб оплати за замовчуванням — «Оплата при отриманні» (накладений платіж).

При кліку «Підтвердити замовлення» → `POST /api/orders` → **401**, тому що:

```ts
export async function registerOrdersRoutes(app: FastifyInstance) {
  app.addHook('preHandler', requireAuth)   // ← весь модуль вимагає авторизацію, гостьового шляху нема
```

Фронтенд на 401 показує нейтральний тост «Не вдалося оформити замовлення. Спробуйте ще раз.» — користувач не розуміє, що причина в відсутності логіну.

**Це реальний конверсійний блокер**: гість заповнює повну форму (ім'я/телефон/місто/відділення), тисне кнопку — і отримує незрозумілу помилку замість «Увійдіть або зареєструйтесь, щоб оформити замовлення».

**Варіанти фіксу** (на вибір): або (а) гейтити `/checkout` логіном/реєстрацією ще на вході, або (б) додати на бекенді гостьовий шлях створення замовлення (guest email/phone, без `userId`), або (в) мінімум — ловити 401 на фронті і показувати конкретний заклик увійти замість generic-тоста.

## 4. [FIXED] Гостьова корзина/обране «зникають» після перезавантаження сторінки

**Де:** `stores/cart.ts:14-31, 176-182` (і, ймовірно, аналогічний стор для wishlist)

Товар і wishlist-id коректно лежать у `localStorage` (`nexus:cart`, `wishlistGuest`) — перевірено напряму через `localStorage.getItem`. Але після **будь-якого** full page reload / прямої навігації по URL шапка (бейджі кошика/обраного) і сторінка `/cart` показують 0/порожньо, хоча дані в сховищі цілі.

Класична проблема Nuxt SSR + Pinia: на сервері `process.client` = false → `_loadLocal()` не викликається → стор серіалізується з порожнім `items`. При гідратації клієнта це порожнє SSR-значення, схоже, перезаписує те, що встиг підвантажити клієнтський `_loadLocal()`.

**Підтверджено ізольовано:** в межах однієї живої SPA-сесії (додав товар → перейшов у `/cart` кліком по іконці, без reload) все відображається правильно — сума, товар, кнопка «Оформити замовлення» активна. Ламається саме на reload/прямій навігації.

**Наслідок:** будь-який гість, що оновить сторінку (F5) або перейде за прямим лінком, побачить «порожню» корзину, хоча товар нікуди не подівся — виглядає як втрата кошика.

**Оновлення (той самий день):** причину підтверджено напряму — тимчасово додав `console.log` у `_loadLocal()` і в блок ініціалізації стора, відтворив баг, і в логах чітко видно послідовність: сервер рендерить `items=[]` → клієнтський `_loadLocal()` коректно ставить `items.value` з 1 товаром → одразу після цього спрацьовує `watch(items, ...)` з новим значенням `[]` — тобто щось перезаписує вже заповнений стан одразу після `setup()`. Це точно відповідає відомій проблемі гідратації Nuxt + Pinia (порожній серverver-стан перезаписує клієнтський після хука `setup`).

**Фікс застосовано:** `stores/cart.ts` — `items` обгорнуто в `skipHydrate()` з Pinia (`const items = skipHydrate(ref<CartEntry[]>([]))`), що виключає це поле з серверної гідратації стану. Перевірено двічі (підстановка в `localStorage` напряму + реальний клік «Додати до кошика») з повним перезавантаженням сторінки — товар тепер коректно відображається і в бейджі шапки, і на `/cart`. Діагностичні `console.log` видалено, у диффі залишився тільки сам фікс (1 імпорт + обгортка `items` + коментар).

## 5. [Minor] Нерелевантні рекомендації на сторінці товару

Сторінка Bluetooth-навушників Logitech G435 (`/product/9361`):

- «Вигідний комплект» пропонує в парі автомобільний зарядний пристрій акумулятора.
- Блок «Схожі товари»/«Рекомендуємо» показує тільки USB LED-лампочки для ноутбука.

Схоже на проблему підбору схожих товарів/бандлів (або артефакт тестових даних на бекенді) — не перевіряв логіку підбору окремо, потребує окремого дослідження.

## Брейкпоінти — mobile / 768 / 1280 / desktop

Перевірено: головна, каталог, картка товару.

- **Mobile (~500px** — `resize_window` на цій машині не сходить нижче ~500px, але це все одно нижче проєктного брейкпоінту `mobile` 640px, тож мобільна розкладка валідна**):** бургер-меню, drawer з «Каталог/Акції/Про нас/Контакти» + «Кабінет» — коректно. Промо-карусель і «Гарячі пропозиції» горизонтально скролляться в межах контейнера (не ламають сторінку). Footer згортається в акордеон. Чисто.
- **768px (tablet):** хедер і hero повертаються до десктопного вигляду, USP-рядок в один рядок, без помилок консолі.
- **1280px (laptop):** каталог — 4-колоночна сітка з фільтрами, картка товару — без змін по суті, без помилок.

Жодних верстальних багів на цих ширинах не знайдено.

**Протокол цих брейкпоінтів тепер закріплено в `.claude/skills/visual-qa/SKILL.md`** — застосовуватиметься автоматично при кожному повному прогоні тестування надалі.
